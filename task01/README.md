## 1. 学习目标与核心问题

本轮 Task01 重点建立 Agent 软件的基本架构坐标，而不是急于开发新功能：

1. **为什么模型会生成 Token，还不足以完成真实任务？**
2. Model、Agent 与 Harness 分别承担什么职责？
3. Coding Agent **产品**与 Agent **Runtime** 为什么不能混为一谈？
4. DSH 的 **Everything Is a Plugin（一切皆插件）**解决了什么工程问题？
5. 四套 Preset 为什么可以共享一个 Runtime，却表现出不同的能力组合？

一句话概括：

> 模型提供智能判断与生成能力；Harness 把模型接入环境，并组织工具、会话、执行反馈等机制，让 Agent 有机会持续、可控地完成任务。

## 2. Model、Agent、Harness：三个层次

| 层次 | 关注的问题 | 典型职责 | 不能直接等同于 |
| --- | --- | --- | --- |
| **Model（模型）** | 下一步生成什么？ | 推理、生成文本或结构化输出、提出工具调用 | 自动执行外部世界的操作 |
| **Agent（智能体）** | 怎样围绕目标持续推进任务？ | 根据输入和反馈决定下一步，协调执行与观察 | 单轮聊天回复 |
| **Harness（运行与组织机制）** | 怎样让上述过程实际运行、可控并可扩展？ | 模型适配、工具接入、会话、执行循环、状态、沙箱与扩展机制 | 单纯的 Prompt 或一个 Tool |

> **注意**：这是便于初学者理解的概念划分，不是 DSH 源码内部严格的一对一组件映射。官方使用“Agent = Model + Harness”说明基本关系，实际产品还有界面及部署等部分。

以“帮我整理一份文旅项目研究材料”为例：

- 模型判断需要哪些资料、哪些证据还不足；
- Harness 提供可用的搜索、文件读取与写入等能力，并管理调用、反馈和记录；
- Agent 在多轮“判断 → 行动 → 观察”中推进工作；
- 最终是否完成，仍需检查真实文件、证据来源及输出质量，不能只凭模型自述。

## 3. Coding Agent 产品与 Runtime 的区别

| 比较项 | 面向用户的 Coding Agent 产品 | Agent Runtime / Harness |
| --- | --- | --- |
| 主要关注 | 用户如何交互、能完成什么任务 | 能力如何组织、执行、组合与管理 |
| 典型内容 | 页面或命令行交互、默认工作流、使用体验 | 模型适配、工具注册、执行循环、状态、插件与权限 |
| 评价重点 | 易用性、任务完成率、体验 | 可扩展性、可组合性、可观察性、控制边界 |

二者不是互斥类别：**一个产品可以建立在 Runtime 之上**。DeepSeek Harness 值得研究的重点，是它把可重用的 Agent 运行能力以插件形式提供，而不是只把自身定位为另一款编程助手。

## 4. Everything Is a Plugin：一切皆插件

根据 DeepSeek 官方介绍，DSH 基于 **Cordis** 插件系统，模型、工具、Skills、会话、沙箱、存储、Agent Loop、调度及 UI 等能力可以作为插件参与组合。

### 4.1 为什么要插件化？

- **职责分离**：模型接入、工具、会话与 Agent Loop 等部分有相对明确的边界；
- **组合复用**：针对不同场景选择能力组合，减少重复搭建；
- **可替换与扩展**：在满足契约的条件下更换或新增实现；
- **生命周期管理**：由 Cordis 管理挂载、卸载及服务依赖，减少对固定单体架构的耦合。

### 4.2 不应误解的地方

- “一切皆插件”不代表所有能力可以**无条件**热插拔，仍需满足接口、依赖和运行状态要求。
- 插件化不自动保证运行安全、答案真实或任务成功；权限控制、沙箱隔离和结果校验仍然重要。
- **Cordis** 负责插件协调；具体 Agent 能力由插件提供，而不是把所有能力都塞进 Cordis 内核。

## 5. 为什么不只是多加几个 Tool？

仅向模型暴露 Tool Calling，解决的是“模型能请求什么操作”。但真实任务还会遇到：

1. 工具调用出错后，怎样反馈并继续？
2. 多轮任务怎样保存会话、执行轨迹与必要的状态？
3. 工具之间如何分工，如何控制权限与执行环境？
4. 如何定位错误、复盘过程、验证是否真正完成？

因此，**Tool 是能力入口，Harness 是组织并运行这些能力的机制**。

DSH 官方还强调可追踪运行轨迹：通过会话日志记录运行中关键的上下文与工具调用，便于检查、恢复、分叉和回放。真实效果仍需结合版本及配置检验。

## 6. 四套 Preset：同一个底座，不同能力组合

以下是 Task01 的**初步认知**；更精确的插件配置与源码逻辑留到后续任务验证。

| Preset | 初步定位 | 适合理解的典型情况 |
| --- | --- | --- |
| **Standard（标准）** | 完整的通用编码 Agent 工具与流程组合 | 常规开发、文件处理、多步研究 |
| **PTC / Code（程序化工具调用）** | 在标准能力基础上，通过 Code Mode SDK 组织多步调用 | 需要把多个工具调用组织为一个程序化流程 |
| **Minimal（极简）** | 只保留少量基本工具 | 在较少运行时干预下观察模型行为 |
| **Creative / Creator（创造）** | 支持检查与扩展运行时，探索自定义 Preset 和插件 | 探索 Harness 自身的可组合架构 |

> **版本说明**：官方页面在部分中英文材料中使用 PTC/Code、Creative/Creator 等不同表述。此处以课程学习常见称呼标注，并以实际安装版本与官方文档为准。

Preset 可以理解为“**预先定义的能力组合**”，不是四个不同的模型，也不只是四组人设提示词。

## 7. 与我的已有 DSH 实践有什么关系？

此前我已实际使用 DeepSeek Harness，并探索过模型配置、工作区和 ACP 接入。我的主要经验偏向“**怎样把工具用起来**”；本章提醒我继续追问：

- 模型与工具的能力究竟在哪里注册？
- 不同 Preset 为什么呈现出不同的工具与工作方式？
- 模型、会话、插件和 Agent Loop 分别由谁管理？
- 当 ACP、插件或依赖出现兼容性问题时，应该先定位哪一层？

对正在建设的个人 AI 工作台与专业研究工作流而言，后续重点不应只是增加模型和工具数量，而应关注**组件边界、权限、可追踪性与可维护性**。

**本轮没有开展新的源码测试或实机对照实验**；上述内容属于基于既有使用经历所做的理解和问题清单。

## 8. Task01 打卡摘要（可按需要摘录）

**学到了什么**

这次学习主要建立了 Model、Agent 与 Harness 的层次认识。模型负责推理与生成，但完成任务需要工具执行、上下文、会话状态以及行动反馈。DSH 采用“一切皆插件”的架构，通过 Cordis 组织模型、工具、会话和执行循环等能力，使同一运行体系能够形成不同的 Preset 组合。

**我的收获**

此前使用 DSH 时，我更关注模型配置、工作区和功能是否能正常使用。现在开始从 Runtime 的视角理解 Agent：真正影响持续任务执行质量的，不只有模型本身，还有系统如何组织工具、记录过程、处理依赖并验证结果。这种架构思维可以逐步迁移到个人 AI 工作台和文旅专业 AI 工作流中。

**下一步**

对照现有 DSH 环境观察四种 Preset 的配置差异；继续学习插件组合和 Cordis 的作用；优先完成官方 Task，而不是额外开发大项目。
